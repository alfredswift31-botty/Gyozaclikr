## Research and design (5 Oct 2026)
Three agents researched in parallel: Apple's APIs, the system-integration layer, and the product and the box. Reports in `docs/research/`. The decisive finding: Apple's on-device Foundation Model takes images on macOS 27 (`Attachment`), verified against Apple's documentation data, so the app leads with Apple Intelligence for pictures and keeps the owner's Qwen3-VL via Ollama as the labelled second engine. Decisions: a deterministic chip row plus a pre-router before any free-text goes to the model; quote verification on every extraction (GyozaYap measured the model inventing items); confirmation cards for anything outward; a self-signed certificate rather than ad-hoc signing, because macOS ties Accessibility and Screen Recording grants to the designated requirement. "Who is this person" and "where can I buy it" are refused by design.

## 1.0: the build (5 Oct 2026)
Scaffold: the project file cloned from GyozaVitals (synchronized folders, Swift 5 mode, default MainActor isolation, macOS 26 minimum), `Core/Model.swift` as the contract between modules, the theme shared with the suite plus the box's tokens, Info.plist with every usage string and the Services entry, the apple-events entitlement, CI on GitHub's `xcode-27` preview runner (macOS 27 SDK; `SDK_MACOS27` set by an SDK-conditional build setting) and on `macos-26` for the text-only build. Four agents then built Capture, Engine, Router + Actions and UI against the contract, each with tests, on their own branches; the coordinator wired them.

**What the agents built and CI proved** (develop green on both runners, 89f8520). Capture: Carbon hot key (tap vs hold through a tested state machine), Accessibility read with a Chromium retry and a ⌘C fallback behind a Secure Input check, region capture with ScreenCaptureKit and a per-display overlay, Vision OCR (proved on the macOS 26 runner: "Gyozaclikr reads 42 words" came back; the macOS 27 preview runner's Vision returns `unknownError`, an anomaly of that image), the Services entry, the two capture permissions. Engine: Apple's model with permissive guardrails for transforms, token budgets and map-reduce chunking, quote-verified extraction, the four tools with a one-outward-action policy, and the macOS 27 image path (`Attachment(cgImage)` inside a `@Generable` description, compiled against the macOS 27.2 SDK on the `xcode-27` runner, compiled out on Xcode 26); Ollama streaming with images; the probe. Router: 68 routing rows including the eight research transcripts, refusals for people, shopping and fact-checking, a relative-date grammar with NSDataDetector as fallback (the detector returns nothing for "next week" or "in 2 hours", measured). Actions: AX replace with a ⌘V fallback, mail compose through the sharing service, EventKit, a Notes AppleScript, Shortcuts, search, the dictionary (a real definition came back on CI), history. UI: the box in nine states, the status item, Settings; 13 snapshot pairs rendered and reviewed against docs/DESIGN.md.

**Integration found two things no module could.** Both Capture and Actions had declared a `PasteboardSnapshot` (the brief had allowed the duplicate; the compiler did not), and the scaffold's Info.plist used a reminders usage key that does not exist: macOS has no add-only level for reminders, so the app asks for full access and the key is `NSRemindersFullAccessUsageDescription`.

**Measured on the runners, to be measured on the Mac next.** Apple Intelligence is unavailable on every GitHub runner (`deviceNotEligible`, even the arm64 preview), so every live-model path, the image probe, `contextSize` and `variant` are unproven until the owner's Engines pane reports them. The first screenshot to ask for is that pane.

**Signing.** 1.0 ships ad-hoc signed from CI, so each update will drop the Accessibility and Screen Recording grants until re-granted. `scripts/resign.sh` re-signs a downloaded build with a self-signed certificate, which keeps the grants; CI signing from a certificate held as a secret is the first 1.0.x change once the owner has made one.

## 1.0.1: the first launch (6 Oct 2026)
The owner opened 1.0, clicked Settings… in the menu, and nothing appeared. The coordinator sent SwiftUI's `showSettingsWindow:` selector, which a menu-bar agent with no key window does not answer on current macOS. Settings is now a window the app owns (`SettingsWindow`, an `NSHostingController` of the same view). Second finding, from reasoning rather than the Mac: the default ⌃Space is macOS's own input-source switch when two keyboard languages are enabled, and Carbon refuses a taken combination silently, so the app would summon nothing and say nothing. Registration now falls back to ⌃⌥Space, then ⇧⌘Space, and the General tab says in red when the saved combination is held by the system. The README gained a "How to use it" section; the first thing a new user asked was how.

## 1.0.2: the crash log (6 Oct 2026)
The owner pasted the crash report for "the app closes on ⌃Space". It was a crash, with a precise trace: `RegionOverlayWindow.init(contentRect:styleMask:backing:defer:)` trapping inside `RegionCapture.captureRegion()`, reached from the hot key's hold path. Two facts in one report. First, the overlay window called AppKit's five-argument `init(…screen:)`, which is AppKit's own convenience: it calls back into the subclass's four-argument initialiser, and Swift stubs that with a trap when the subclass has not overridden it. The overlay now calls the designated four-argument initialiser with a global-coordinate frame, which lands on the right screen anyway. The 1.0.1 guess (the panel closing itself on activation) was wrong about the cause; its change is harmless and stays. Second, a press the owner meant as a tap reached the hold path: 300 ms is less than a hand lingers on a two-key shortcut. The threshold is 500 ms, with a test that a 300 ms press is a tap. Lesson, again: one crash log beat an hour of reading code.

## 1.0.3: the pointer gyoza (6 Oct 2026)
The owner asked for a sign that the app is open: "a small olive green gyoza hologram floating near the pointer". `PointerCompanion` is a 30-pt click-through panel on every Space that follows the pointer through a global mouse-moved monitor (no permission), 14 pt right and 26 pt below the tip, hidden while the box or the region overlay is up, with a toggle in Settings › General (on by default). The glyph is the suite's gyoza in olive over a blurred olive glow at 85 %. The bob is a Core Animation on the panel's layer, so the render server moves it and the app never redraws: GyozaVitals' lesson about a SwiftUI repeat-forever animation costing a tenth of a core was fresh. Reduce Motion gets a still glyph. Also: the 40 ms token-coalescer test, which failed once on a loaded Xcode 26 runner, now polls for up to a second.

## 1.0.4: the Engines pane answers, the box still hides (6 Oct 2026)
**Measured on the owner's Mac (M4, 16 GB, macOS 27.0.1), from the Engines pane of 1.0.3:** Apple Intelligence ready; context **8192 tokens** (the WWDC26 slide was right, Apple's 4K table was stale); variant **AFM 3 Core Advanced**; **image input: supported**; 24 languages. Ollama reachable with five models, vision model `huihui_ai/qwen3-vl-abliterated:8b-instruct`. The project's one open question is closed: Apple's on-device model takes pictures on this Mac.

**Still open:** on ⌃Space the olive gyoza steps aside (so the hot key fires and `summon` runs) and no box appears; no crash report is written. The panel was ordered front at alpha 0 and relied on a window animation to fade in; if that animation does not run, the box is on screen and invisible, which looks exactly like this. 1.0.4 drops the fade (alpha 1, `orderFrontRegardless`, a size floor) and, instead of a third guess, instruments: 300 ms after every summon the coordinator records the panel's visibility, key state, alpha, frame, screen and the hot key's registration into the Engines pane ("Box") and the unified log under subsystem `com.gyoza.Gyozaclikr`. The next screenshot says what the box did.

## 1.0.5: the first real press (6 Oct 2026)
1.0.4's box appeared: the fade was the cause of the invisible box. The owner selected a sentence in a chat app and typed "change this into formal writing". Two faults in one screenshot. Accessibility had never been granted, and the app had never asked: the system dialog only ran from the Grant button. Now the first denial asks macOS directly (the standard "would like to control this computer" dialog), and the failure line names the exact pane. Second, with nothing read, the request still went to the model wrapped around an empty ⟪⟫ fence, and the model dutifully rewrote the fence: "The specified content is located between the delimiters…". `Prompts.userPrompt` now fences only a non-empty selection, and a request that refers to the selection ("change this", a chip) over nothing is refused with the reason before any model runs; a standalone question still goes through.

Third fault, from the next two screenshots: the first answers came back right (“The double of 123 is 246”, a synonym), clipped on both sides. The card widens from 360 to 480 pt when an answer arrives, and the window did not follow, so the wider card sat centred in the old frame. The panel now observes the model (state, answer, outcome, proposal, chips) and refits the window to the card's fitting size on every change.

## 1.0.6: read before showing (6 Oct 2026)
Accessibility granted, text selected in TextEdit, and 1.0.5 still read nothing. The coordinator showed the box first (the 100 ms budget) and read after; the box takes key, so the Accessibility read of the focused element and the simulated ⌘C both landed on the box's own empty field. The order is now read, then show: an Accessibility read takes milliseconds, the ⌘C fallback at most 150 ms, both inside the budget. The design note in docs/DESIGN.md ("capture runs after showing") was wrong for a box that takes keyboard focus.

## 1.0.7: the clipped answer, second attempt (6 Oct 2026)
1.0.6 read the selection (the quote appeared, the model made it formal) and the answer was still clipped on both sides. 1.0.5's refit measured the hosting view's fitting size when the observation fired, which is before SwiftUI renders the change, so it measured the old 360-pt layout and kept the old width. The panel now takes its width from the state alone (360, or 480 with an answer), applies it at once, measures the height now and again 60 ms later, and no longer lets the hosting view size the window (its own sizing fought the panel's).

## 1.0.8: the card reports its size (6 Oct 2026)
1.0.7's width was right and the action row was cut off below: the hosting view's fitting height lagged the real layout even 60 ms later. The card now reports its rendered size itself (`onGeometryChange` on the card's root), and the panel follows that: SwiftUI's own measurement after layout, not AppKit's estimate before it. Three releases on one window's size is the cost of sizing a SwiftUI card from AppKit by inference; the reporter should have been the first design.

## 1.0.9: both image engines, measured (6 Oct 2026)
The owner drew a region around a driving-theory illustration (two cars, a red arrow labelled “2 seconds”) and asked “what is this?” twice. **Apple, on-device, macOS 27:** “A red and a blue car on a road. a road with grass on either side. Text: 2 seconds.” Correct and literal, in a few seconds; the constrained fields (subject, setting, visible text) kept it honest and kept it from interpreting. **Ollama, Qwen3-VL-8B:** “This is an illustration showing the 2-second rule for safe following distance while driving…”, with the violet edge and the model name as designed. The first measurement of the project's central trade-off: Apple describes what is there, the 8B vision model explains what it means. Changes: the Apple description gains a `meaning` field (“what it is for or explains, only when the image makes it clear”) and the renderer capitalises each fragment into a sentence; under an Apple image answer, when Ollama is reachable, an “Ask Ollama” button re-asks the same question through `/local`. Apple stays the default for images: seconds, not tens of seconds, and nothing to run.

Also in 1.0.9, at the owner's request: the box is draggable by its background and stays where it was put (a dragged box keeps its top-left corner as it grows), it no longer closes on a click elsewhere or an app switch, and a × in its corner (or Esc, or ⌘W) closes it. The 1.0 design closed on any click outside, which reads well in a spec and badly when an answer is wanted beside another window.

And the box is now a conversation, not a single exchange. The owner's complaint: to ask a second thing he had to delete the first question and type over it. Each send now becomes a turn (request in grey, answer below, a hairline between), the field clears for the next one, and the turns scroll inside the box at up to 300 pt. Free-text follow-ups carry the last four answered turns into the prompt (“Earlier in this conversation: User… Assistant…”, capped at 2,000 characters in total) so “make it shorter” after a rewrite means that rewrite; chips do not carry history, since a chip is a fresh instruction on the selection. The 4k-token context of Apple's model is the reason for the cap and the four-turn window: the selection still has to fit beside the history.

## 1.0.10: the drag that never started, and mail through a browser (6 Oct 2026)
The owner reported 1.0.9: the conversation and the × work, the drag does not. `isMovableByWindowBackground` asks the view under the pointer whether a mouse-down may move the window, and an `NSHostingView` answers no (it owns its events for SwiftUI), so the panel never moved; the snapshot could not have shown that. The card now carries a `DragGesture` of its own at the lowest priority: buttons, the field and text selection are inner gestures and win, anything else drags. The gesture reports the pointer's displacement in screen coordinates (its own translation is relative to the window, which is what is moving) and the panel sets its origin from that; the move posts `didMove`, which already marked the box as the user's to keep in place.

Send… opened Chrome and nothing else. The default `mailto:` handler on the owner's Mac is Chrome (Gmail), and `NSSharingService.composeEmail` hands the message to the handler's share extension, which a browser does not have: the app activates, the message is lost. `MailCompose` now checks the handler: Apple Mail keeps the sharing service (no length limit), anything else gets an RFC 6068 `mailto:` URL with recipients, subject and a CRLF body, the one compose request a browser understands. Web mail cuts long links, so a body over 1,800 characters goes to the clipboard as well and the outcome line says so. The research (§5) called the sharing service the no-permission path; it is, for Mail, and a browser as the mail handler was the case it did not cover.

## 1.0.11: questions may leave the selection (6 Oct 2026)
The owner captured a driving-theory list about road studs, asked about the image, then asked “what if I cross the white line?” and got “The text does not specify what happens if you cross the white line.” That sentence is the instruction's: “if the request needs facts that are not in the selected text, say so in one line instead of guessing”, written to keep rewrites honest, applied to every question too. The rule now splits by request: rewriting, summarising and extracting use only the selection and add nothing; a question is answered from the selection when it covers it, otherwise from the model's own knowledge, prefixed “From general knowledge:” so the owner can see which. No selection means a general question. The prefix is the trade: a 3B on-device model answering from memory can be wrong, and the label is what keeps a selection-grounded answer distinguishable from a guess. The owner's framing was right: the box is a place to ask anything, with the selection as context, not a cage.

## Where things stand (6 Oct 2026, twelve releases in)
Twelve releases in one night, ten of them from the owner's screenshots, reports and one crash log. **Verified on the Mac (M4, 16 GB, macOS 27.0.1):** the olive gyoza beside the pointer; the hot key; the box under a selection with its quote and token count; a free-text rewrite ("write this in formal") and a question ("what would be the double of this") answered by Apple's on-device model, labelled; the Engines pane with context 8192, variant Core Advanced, image input supported, Ollama reachable with Qwen3-VL; the Accessibility grant and the read of a TextEdit selection; region capture with Screen Recording, the thumbnail and Live Text ("OCR · 44 words"), the image chips. **Not yet seen:** Replace writing back into the document; a chip; a reminder's confirmation card and the EventKit prompt; the Services entry; long answers scrolling.

**Verified in 1.0.9 and 1.0.10, from the owner's reports:** the conversation in the box (follow-ups answered in the same box, the field clearing after each send); the × closing it; the drag, once the card got its own gesture; Send… opening a Gmail compose window in Chrome with the text in the body, after the owner allowed Gmail as Chrome's mailto handler (a one-time browser prompt, not something the app can grant). **Still not seen:** Replace writing back into the document; a chip; a reminder's confirmation card and the EventKit prompt; the Services entry.

**Lessons from the night.** Every fix came from the Mac: a crash log named the overlay initialiser; a screenshot showed the model rewriting an empty fence; another showed the box reading its own field. Three releases went into one window's size because AppKit was guessing at a SwiftUI layout; the card reporting its own size should have been the first design. Two more features that read well in the snapshot did nothing on the Mac (the drag, Send…), for the same reason: the snapshot renders the card and cannot press it, and the research named the AppKit facility without checking it against a SwiftUI host or a browser as the mail handler. The CI can prove layout; only the Mac proves behaviour, and the owner's report is the test. The ad-hoc signature costs a re-grant on every update, as the research said it would; the certificate is next.
